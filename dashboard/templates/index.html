🔌 OWASP API Security Top 10 · 2023

The OWASP API Security Top 10 focuses on strategies and solutions to understand and mitigate the unique vulnerabilities and security risks of Application Programming Interfaces (APIs).

APIs expose application logic and sensitive data, making them increasingly attractive attack targets.

10
Categories
Labs coming soon
API1:2023
Broken Object Level Authorization
OFFLINE

APIs expose endpoints handling object identifiers, creating a wide attack surface. Authorization checks should be performed in every function that accesses a data source using input from the user.

BOLAIDORAuthorization
API2:2023
Broken Authentication
OFFLINE

Authentication mechanisms are often implemented incorrectly, allowing attackers to compromise authentication tokens or to exploit implementation flaws to assume user identities temporarily or permanently.

TokensJWTSessions
API3:2023
Broken Object Property Level Authorization
OFFLINE

Combination of Excessive Data Exposure and Mass Assignment. Lack of property-level authorization allows attackers to read or modify object properties they should not have access to.

Mass AssignmentData Exposure
API4:2023
Unrestricted Resource Consumption
OFFLINE

Satisfying API requests requires resources such as network bandwidth, CPU, memory, and storage. Lack of restrictions on request size or frequency can lead to DoS or increased operational costs.

Rate LimitingDoSThrottling
API5:2023
Broken Function Level Authorization
OFFLINE

Complex access control policies with different hierarchies, groups and roles, and an unclear separation between administrative and regular functions tend to lead to authorization flaws.

BFLAPrivilege Escalation
API6:2023
Unrestricted Access to Sensitive Business Flows
OFFLINE

APIs vulnerable to this risk expose a business flow — such as buying a ticket or posting a comment — without compensating for how the functionality could harm the business if used excessively.

Business LogicAutomation Abuse
API7:2023
Server Side Request Forgery
OFFLINE

SSRF flaws occur whenever an API is fetching a remote resource without validating the user-supplied URL. This enables attackers to coerce the application into sending a crafted request to an unexpected destination.

SSRFInternal Network
API8:2023
Security Misconfiguration
OFFLINE

APIs and the systems supporting them may contain misconfigurations that can be exploited by attackers: unnecessary HTTP methods enabled, permissive CORS policies, verbose error messages revealing sensitive information.

CORSHTTP MethodsHeaders
API9:2023
Improper Inventory Management
OFFLINE

APIs tend to expose more endpoints than traditional web applications, making proper documentation and inventory critical. Outdated or undocumented endpoints — shadow APIs — often lack security controls.

Shadow APIsVersioningDocumentation
API10:2023
Unsafe Consumption of APIs
OFFLINE

Developers tend to trust data received from third-party APIs more than user input. APIs that interact with external or third-party APIs should be treated with the same security standards applied to user input.

Third-party APIsTrustValidation

🐳 Container & Kubernetes Security

Containers and orchestration platforms introduce a unique attack surface. Misconfigurations, overpermissioned workloads and insecure defaults can lead to container escapes, cluster takeover and data exfiltration.

This track covers the most critical vulnerabilities found in real Docker and Kubernetes environments.

10
Categories
Labs coming soon
CK01
Exposed Docker Socket
OFFLINE

Mounting /var/run/docker.sock inside a container grants full control over the Docker daemon, enabling container escape and host compromise.

Container EscapeDocker SocketPrivilege Escalation
CK02
Privileged Container Escape
OFFLINE

Containers running with --privileged flag or with dangerous Linux capabilities (SYS_ADMIN, SYS_PTRACE) can mount the host filesystem and escape to the underlying node.

--privilegedLinux CapabilitiesHost Mount
CK03
Secrets in Images & Environment Variables
OFFLINE

Hardcoded credentials in Dockerfiles, image layers or environment variables are extractable via docker inspect or image layer analysis, even after deletion.

SecretsImage LayersENV vars
CK04
Vulnerable & Outdated Base Images
OFFLINE

Using outdated or unpatched base images introduces known CVEs into every container derived from them. Without image scanning in the CI/CD pipeline, vulnerable images reach production undetected.

Base ImagesCVE ScanningSupply Chain
CK05
Kubernetes RBAC Misconfiguration
OFFLINE

Overpermissioned service accounts, wildcard permissions and cluster-admin bindings allow lateral movement and privilege escalation within a Kubernetes cluster from a compromised pod.

RBACService Accountscluster-admin
CK06
Exposed Kubernetes Dashboard
OFFLINE

The Kubernetes Dashboard exposed without authentication or with overpermissioned service accounts allows unauthenticated attackers to deploy workloads, read secrets and take over the cluster.

K8s DashboardNo AuthCluster Takeover
CK07
Kubernetes API Server Exposure
OFFLINE

An unauthenticated or anonymously accessible Kubernetes API server allows an attacker to list and modify all cluster resources. Combined with RBAC flaws, this provides full cluster control.

API ServerAnonymous Authkubectl
CK08
Namespace Isolation Failures
OFFLINE

Missing NetworkPolicies allow pods in different namespaces to communicate freely. A compromised pod in a low-privilege namespace can reach sensitive services in other namespaces or the host network.

NetworkPolicyNamespaceLateral Movement
CK09
Container Resource Exhaustion
OFFLINE

Containers without CPU and memory limits can consume all node resources, causing a denial of service to co-located workloads. A fork bomb or memory leak in one container can take down the entire node.

Resource LimitsDoSFork Bomb
CK10
Image Registry Attacks & Unsigned Images
OFFLINE

Pulling images from untrusted or compromised registries without signature verification allows supply chain attacks. Attackers can replace legitimate images with malicious ones that execute code on container startup.

Image SigningRegistrySupply Chain

🎮 How it works

🧪 Labs

Each lab is a standalone Docker container running a realistic corporate application — no vulnerability labels, no hints in the UI. Start a lab from the dashboard, attack it as a real pentester.

🚩 Flags

Hidden inside the app data. Only accessible by successfully exploiting the vulnerability. Format: FLAG{...}

🪙 Dinocoins & Hints

Each flag submitted awards Dinocoins (100–200 🪙). Dinocoins unlock hints — three progressive levels per lab. Completing a lab automatically unlocks the first hint of the next one.

🏆 Hall of Fame

Submit your score via a pre-filled GitHub Issue. A GitHub Action processes it automatically and updates the public leaderboard.

🚀 Platform Vision

DinosecLabs is designed as an extensible security training platform, not just a one-off lab set. The OWASP Top 10 2025 is only the first module. The architecture supports independent, plug-and-play training tracks that can be added, updated or removed without changing the core platform.

Each Track is a self-contained collection of Docker labs sharing a theme — a vulnerability class, a technology stack, a certification path or a specific attack scenario. Tracks live independently in the repo and are loaded dynamically by the dashboard.

      ├── track.json    # name, description, labs list
      ├── labs/
      │   └── lab-01/    # Dockerfile + app
      └── flags.json   # flag registry + hints
